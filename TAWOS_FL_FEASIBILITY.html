Section 01

Data Extraction & Features

Option A

Tabular Features

Extract structured numerical and categorical features directly from TAWOS database issues via SQL queries.

  • Example features: description length, comment count, link count, assignee changes, resolution time, sprint duration
  • Format: CSV — features (columns) x issues (rows)
  • Effort: Low — SQL queries to CSV
  • Lightweight and easy to distribute
  • Reproducible across workers
  • Ideal for federated environments

Option B

Text Embeddings

Convert issue descriptions into high-dimensional numerical vectors using BERT or Sentence Transformers.

  • Output: 768-dimensional vector per issue
  • Format: Large numpy arrays
  • Effort: Medium — requires embedding model
  • Overkill for MVP
  • Storage intensive
  • Harder to distribute across workers
Recommendation: Option A (Tabular Features) — simplest and most effective starting point
Section 02

Task Type

Option A

Regression

Predict exact story point values as continuous numbers. TAWOS provides actual SP values, making this a natural fit.

  • Model output: Continuous number → round to nearest SP
  • Loss function: MSE (Mean Squared Error)
  • Evaluation: RMSE, MAE
  • Most common in industry
  • Matches agile estimation reality
  • Preserves full numeric precision

Option B

Classification

Categorize issues into SP buckets such as Small, Medium, or Large classes.

  • Model output: Probability per category
  • Loss function: Cross-Entropy
  • Evaluation: Accuracy, F1-Score
  • Loses granularity
  • Treats SP as discrete categories vs. continuous scale
Recommendation: Regression — preserves precision and aligns with agile practice
Section 03

Model Architecture

For federated learning on tabular data, a Multi-Layer Perceptron (MLP) is the optimal choice. It integrates cleanly with FedAvg and requires no change to the existing aggregation infrastructure.

20 Input Features
Input Layer
→
128 neurons · ReLU
Hidden Layer 1
→
64 neurons · ReLU
Hidden Layer 2
→
1 neuron · Linear
Output (SP Prediction)

Why MLP

  • Works well for tabular data
  • Easy parameter aggregation with FedAvg
  • Drop-in replacement for CNN
  • Fast training, small footprint (~20k params)

Why Not Others

  • BERT (Transformers) — You have numerical features, not raw text. BERT's entire purpose is to convert text descriptions into vectors. Adding BERT means: extra preprocessing, loading 100M+ parameters per worker, slower training, and bloated model aggregation. It solves a problem you don't have.
  • XGBoost — Tree-based models are hard to federate. Parameters aren't continuous and don't aggregate well with FedAvg. You'd need custom aggregation logic and lose the benefits of your existing framework.
  • Linear Models — Too simple for the relationships in your 20 features. Won't capture non-linear patterns, leading to poor RMSE and underperformance compared to MLP.
Recommendation: Custom PyTorch MLP — retain existing FedAvg infrastructure unchanged
Section 04

Data Distribution Strategy

Option A

By Project

Each worker receives all issues from a specific project. 39 available projects — use 10–15 major ones.

  • Non-IID (realistic)
  • Simulates real team collaboration
  • Demonstrates FL heterogeneity

Option B

Random IID

Shuffle all 450K issues and divide equally across workers.

  • Simpler setup
  • Unrealistic for real teams
  • Misses heterogeneous data challenges

Option C

By Issue Type

Partition by Bug vs. Feature across workers.

  • Logically motivated
  • Less natural than project boundary
  • Fewer distinct partitions
Example — By-Project Distribution
Worker 1  →  Apache Mesos       (~5,000 issues)
Worker 2  →  Apache MXNet        (~6,000 issues)
Worker 3  →  Atlassian Confluence (~7,200 issues)
Worker 4  →  Spring Framework    (~4,800 issues)
...
Worker N  →  Last major project
Recommendation: Option A (By Project) — most realistic simulation for FL research

Section 07

Implementation Plan

Data Pipeline Overview

01 🗃 TAWOS MySQL Database — source of all issue data ↓
02 📊 Feature Extraction — SQL queries yield ~20 tabular features per issue ↓
03 📄 CSV Dataset — 450K rows x 20 columns ↓
04 ⚙ Project Partitioning — distribute across 10–15 workers by project ↓
05 📈 Local MLP Training — each worker trains on their project subset ↓
06 🔗 FedAvg Aggregation — server averages model parameters across workers ↓
07 ✓ Global Model — predicts story points for any new issue

Phase-by-Phase Breakdown

Phase 1 — Data Preparation (Day 1)

  • Download TAWOS database SQL file
  • Create tawos_feature_extractor.py
  • Run extraction → data/tawos_features.csv
  • Verify: 450K rows, no missing values

Phase 2 — Data Loaders (Day 1–2)

  • Create tawos_data_loader.py
  • Partition CSV by 15 major projects
  • Build and pickle DataLoaders per worker

Phase 3 — Model (Day 2)

  • Create TAWOSMLP in federated_learning/nets/
  • Verify shape: (batch=32, features=20) → (batch=32, output=1)

Phase 4 — Framework Integration (Day 2–3)

  • Update arguments.py with TAWOS dataset option
  • Adjust client.py evaluation → RMSE / MAE
  • Update API server with TAWOS endpoints

Phase 5 — Testing (Day 3–4)

  • Run via CLI with TAWOS config
  • Run via API: POST /run-experiment with dataset=tawos
  • Verify results in results/ folder

Phase 6 — Validation (Day 4–5)

  • Train global model for 50 rounds
  • Confirm RMSE decreases consistently
  • Compare federated vs. single global baseline
  • Verify non-IID effect visible across workers
Section 08

Expected Results & Success Criteria

Output Metrics

  • Per round: Global RMSE, Global MAE, Test Loss
  • Per worker: Local RMSE, Training Loss
  • Participation log: Active workers per round
  • Format: CSV saved to results/ folder

Success Criteria

  • RMSE improves over 50 rounds (e.g. 5.0 → 3.2)
  • Federated RMSE outperforms single global baseline
  • Worker convergence visible in logs
  • Non-IID effect detectable across worker optima

Final Verdict

The existing federated learning framework is sufficiently flexible. The core algorithmic components require no changes — only the data pipeline and model architecture need replacing.

In essence: swapping "What class is this image?" for "What story points for this issue?" — the FL machinery stays intact.

+Server, Client, FedAvg, API, and Web UI are fully reusable
+No algorithmic changes to aggregation logic
+Main work scoped to data loading and model swap
+Working proof-of-concept in 3–5 days
